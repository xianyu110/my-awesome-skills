这是一套为自家产品站做 GEO 的闭环：先把真实需求挖准，再按细分问法批量做概览页和 Q&A，上线后用收录和收入做归因和自动维护。用户对自己产品的需求通常很明确；任务是把这个需求对齐到用户真正在问的问题上。

## 原则

- 先弄清真实问法和痛点，再写页面。不要凭空编用户原话、排名、价格或测评分数。
- 产品边界以用户说定的为准：能做什么、不能做什么、合规红线，都要写进页面，不要承诺做不到的事。
- 优先做厚的概览枢纽和配套 Q&A，针对细分问法和不同人群；不要为了凑量用同一骨架批量生产薄页。
- 上线只是开始。新页面会被搜索和对话模型较快抓取，但起不起量要看实际收录和收入。
- 事实以现网和官方页为准，发布前再核一遍。站点上已有的明显错误（坏链、过期价、错误口径、占位正文）要先修或一起修，不要让新文跟错误现网打架。

## 1. 从竞品和好页面挖真实痛点

- 先确认产品能力、价格或套餐、合规边界，以及该站已有哪些页面。
- 批量查竞品和本站已经表现好的页面：标题、FAQ、对比、定价说明、评价和帮助文档里反复出现的问题。用户可以理解的问法要保留原话感，不要改写成营销口号。
- 整理成优先主题清单：问法、人群或场景、是否已有页面覆盖、建议新建枢纽还是并入已有页（避免互相抢收录）。
- 先把清单交给用户确认，再进入批量写作。不要一下子把所有长尾铺开。

## 2. 按细分问法批量做概览页和 Q&A

- 需求确认后，按优先主题批量写作。每个主题做一篇厚枢纽：把问题说清楚、给可执行的步骤、写清产品边界、配上 FAQ。不同人群或场景可以拆页，但要真正写出差异，不要只换几个词。
- 规模可以很大，但质量要跟上：同一问法不要复制出一大片近似页；只在该问法确实有对应市场时加语言版，不要把薄页机翻成一堆语言版本。
- 先当草稿：核对现网价格、能力、计费口径和法律文案。政策没写清的事，就写「政策未说明」。指向尚未上线的内页不要做成死链。
- 用户确认发布后，再写入站点自己的页面系统，补上 sitemap、llms.txt、canonical / hreflang、必要的 JSON-LD，并提交收录（如 IndexNow）。用该站既有的账号和部署流程，不要部署到错误账号或环境。未经说明不要改计费逻辑和标价。

## 3. 用收录和收入归因，把维护跑成闭环

- 看实际收录（是否进索引、是否被抓取）和收入或转化（哪些页带来注册、订阅或订单）。数据源没连上时，说清缺什么，再请求对接或让用户提供。
- 转化好的方向：加厚该页、补内链，并沿同一需求继续扩相关枢纽和 Q&A。
- 没收录或有问题的页面：查规范标签、索引屏蔽、内容过薄、互相抢词、技术错误，修好或合并，不要放着不管。
- 把「再挖问法 → 再写页 → 再看数据」当成持续循环，而不是一次性交稿。有稳定数据源时，可以建定时检查。

## 交付时

- 调研阶段：交优先主题清单和依据，等确认再写。
- 写作阶段：先交草稿路径和要点，确认后再发布、提交收录。
- 维护阶段：说清加码了哪些方向、处理了哪些未收录或有问题的页，以及下一轮建议扩的主题。
